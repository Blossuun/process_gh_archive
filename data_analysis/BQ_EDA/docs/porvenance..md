# 무엇을 어떻게 알아냈는가

`query/` 와 스크립트가 각각 무엇을 만들었고 거기서 무엇이 나왔는지.
BigQuery 사용량은 총 **19.64 GB**, 월 무료 한도 1TB 의 2% 다.
비용은 `query_log.csv` 에 기록된 실제 청구량이다.

---

## 쿼리

실행은 전부 `uv run run_query.py query/<파일>.sql`.
결과는 `results/<파일명>.json`, 비용은 `query_log.csv` 에 기록된다.

### `table_inventory.sql` — 0 B

`__TABLES__` 메타데이터로 day 테이블 5,663개의 날짜·행 수·크기를 받는다. 메타데이터 조회라 스캔 비용이 없다.

**알아낸 것**
- 데이터셋 범위 2011-02-12 ~ 2026-08-27
- 2016-06-23 까지는 일괄 마이그레이션분, 2016-06-24 부터 일일 자동 적재
- 결측 8일 (2016-07 이후 기준)

**어디 쓰이나** — 이후 모든 로컬 분석의 원천. `analyze_inventory.py` 의 입력이며, BigQuery 를 다시 부르지 않고 결측·이상일·볼륨 추이를 전부 계산한다.

### `schema_signature.sql` — 10 MB

`INFORMATION_SCHEMA.COLUMNS` 로 테이블마다 컬럼 구성 지문을 만들어 묶는다. 묶음 개수가 곧 서로 다른 스키마의 개수다.

**알아낸 것**
- 묶음이 1개. 15년간 테이블 레벨 스키마가 한 번도 안 바뀜
- 따라서 이후 발견되는 변화는 전부 payload 내부이거나 이벤트 구성비 문제
- 부수적으로 9개 컬럼 구성 확정. `repo`·`actor`·`org` 가 STRUCT 라 payload 없이 읽을 수 있다는 사실이 여기서 나왔다

### `hourly_completeness.sql` — 304 MB

19일을 골라 시간대별 이벤트 수를 센다. GH Archive 원본이 시간당 파일이므로, day 테이블이 존재해도 일부 시간이 안 들어왔을 수 있다.

**알아낸 것**
- 결측일 앞뒤가 실제로 부분 적재였다. 2021-08-27 은 24시간 중 23시 한 시간만 존재
- 장애 구간을 시간 단위로 복원 (예: 2020-08-21 09시 ~ 08-23 15시, 약 55시간)
- **일교차 소멸**: 정상일은 최저/최고 시간 비율이 0.55~0.58 인데 2026-07-15 는 0.93. 사람 활동이라면 나올 수 없는 평탄함
- 생성 지연은 데이터 누락과 무관했다 (2018-04 사례). 위양성으로 판명

### `type_trend_quarterly.sql` — 1.55 GB

2016 Q3 ~ 2026 Q3, 분기당 하루씩 41일의 이벤트 타입별 건수.

**알아낸 것**
- **WatchEvent 붕괴**. 2024-11-13 하루 271,792건이 정점이고 2026-08-12 에는 2,555건
- ForkEvent, PullRequestEvent 도 같은 곡선. PushEvent 만 오히려 증가
- PR 이 97% 줄었는데 push 가 늘었다는 조합은 현실에서 불가능하므로 수집 문제로 확정

### `type_trend_monthly.sql` — 1.76 GB

2024-09 ~ 2025-12, 월 2일씩 32일. 분기 표본으로 좁혀진 경계를 월 단위로 확정한다.

**알아낸 것**
- **2025-05 중순 40% 균일 감소**. 15개 타입 전부가 0.49~0.65 사이 같은 비율로 감소. 균일하므로 비율 지표는 보존됨
- `DiscussionEvent` 가 2025-10-22 부터 등장. 타입 목록이 고정이 아니라는 증거

### `payload_keys_before.sql` — 12.63 GB / `payload_keys_after.sql` — 3.10 GB

2025-09-24 와 2025-11-12 의 payload 키 구조와 타입별 평균 길이. 같은 쿼리를 두 날짜에 돌린다.

**알아낸 것**
- **payload 축소의 정체**. 가중 평균 3,481B → 927B. 인벤토리의 행당 바이트 하락(3,683 → 1,199)을 거의 그대로 설명한다
- PushEvent 의 `commits` 배열 삭제, `pull_request` 48개 필드 중 43개 삭제
- **필드 이동 발견**: `pull_request.labels` → `labels`. 커버리지가 100% 에서 39% 로 떨어졌지만 손실이 아니라 표현 방식 변경
- 변화가 PR 계열과 PushEvent 에만 집중됐고 나머지 11개 타입은 그대로

**비용 메모** — 두 날짜를 `UNION ALL` 로 합치고 `TABLESAMPLE` 을 걸었더니 dry run 은 758MB 를 보고했지만 실행은 15.7GB 를 요구했다. 표본은 과금을 줄이지 못한다. 파일을 둘로 나누고 표본을 뺀 이유다.

### `other_column_stats.sql` — 305 MB

한 번도 안 본 `other` 컬럼의 널 비율, 평균·최대 길이, 고유값 수.

**알아낸 것**
- `{"actor":{"display_login":"..."}}` 고정 구조. 평균 42B, 최대 69B, 존재율 100%
- **비용 추정을 틀렸다.** 컬럼이 작아 수 MB 로 예상했지만 730만 행이라 305MB 였다.
  컬럼 폭이 좁아도 행이 많으면 비용이 붙는다
- 사라진 payload 필드가 이쪽으로 옮겨가지 않았음을 확인. 커밋 배열이 들어갈 크기가 아니다
- 분석 가치 없음. drop 대상

## 스크립트

### `run_query.py`

`.sql` 하나를 실행하고 비용을 기록한다. **dry run → 상한 검사 → 실행** 순서로 동작하며, 예상 스캔량이 상한을 넘으면 실행하지 않는다.

**여기서 배운 것**
- 상한이 실제로 두 번 막았다. 15.7GB 와 13.5GB 요구 시점에 과금 0 으로 중단
- 초과 시 에러가 실제 필요량을 알려주므로, **상한을 낮게 걸어 비용을 미리 알아내는 탐침**으로 쓸 수 있다
- `TABLESAMPLE` 쿼리에서는 dry run 추정치를 믿으면 안 된다

### `fetch_sample_rows.py`

`tabledata.list` API 로 원본 행을 가져온다. 쿼리 잡을 만들지 않으므로 **스캔 바이트가 0** 이다. 같은 일을 SQL 로 하면 하루치가 12.6GB.

**알아낸 것**
- `other` 컬럼의 실제 값을 눈으로 확인
- 2025-11-12 의 PushEvent payload 가 **잘린 문자열이 아니라 온전한 JSON** 이라는 것. 전송 오류가 아니라 의도된 축소
- 산출물 `results/rows_20250924.json`, `results/rows_20251112.json` 은 깊이 3 이상 필드(`pull_request.head.ref` 등)를 확인할 때 계속 쓰인다

### `analyze_inventory.py`

`results/table_inventory.json` 하나로 결측 구간, 일별 적재 이상, 월·연도별 볼륨 추이를 계산한다. BigQuery 를 부르지 않으므로 기준값을 바꿔가며 몇 번을 돌려도 비용이 없다.

**산출물**

| 파일 | 내용 |
|---|---|
| `table_inventory_report.md` | 결측·이상일·볼륨 요약 |
| `daily_volume.csv` | 3,702일 전부의 이동 중앙값 대비 비율과 이상 여부 |
| `monthly_volume.csv` | 월별 행당 바이트·일평균 행 수와 전월 대비 |
| `yearly_volume.csv` | 연도별 집계와 전년 대비 |

**알아낸 것**
- **2025-10-09 ~ 10-14, 6일간 정상의 0.5%**. 결측 검사에도 월별 집계에도 안 걸리던 구간
- 2021-10 장애가 결측일(10/26) 앞의 10/22 부터 시작됐다는 것. 인접일만 봐서는 놓쳤다
- 2026년 8월은 정상일과 이상일이 며칠 간격으로 번갈아 나온다. 현재 적재가 불안정한 상태
- 행당 바이트와 일평균 행 수가 **독립적으로 움직인다**. 급변 시점이 거의 겹치지 않아, 구조 변화와 수집 문제를 구분하는 근거가 됐다

`daily_volume.csv` 는 저장소에 커밋하지 않는다. 파이프라인의 품질 게이팅은 이 파일을 읽는 대신
다운로드한 원본에서 같은 지표를 직접 계산한다. 판정 로직의 근거가 이 EDA 에 있을 뿐,
파일 자체가 의존 대상은 아니다.
