# GH Archive EDA 결과

BigQuery 공개 데이터셋 `githubarchive.day` 를 조사해서, 파이프라인에 무엇을 남기고 분석 창을 어디로 잡을지 정한 기록.

조사 범위는 2016-07-01 ~ 2026-08-27, 3,702일. 그 이전 테이블은 2016년 6월에 일괄 마이그레이션된 것이라 일일 적재분과 성격이 달라 제외했다.

---

## 1. 데이터셋 상태

| 항목 | 값 |
|---|---|
| 테이블 스키마 | 9개 컬럼. 15년간 변경 없음 |
| 이벤트 타입 | 15종. 2025-10-22 부터 `DiscussionEvent` 추가로 16종 |
| 결측일 | 8일 (2020-08, 2021-05·08·10) |
| 적재 이상일 | 59일 / 39개 구간 |
| 일평균 이벤트 | 2024년 493만 건이 정점. 이후 감소 |

적재 이상일은 이동 중앙값(28일) 대비 60% 미만인 날이다. 테이블은 존재하는데 내용이 덜 들어온 날을 잡는다. 목록은 `daily_volume.csv` 의 `is_anomaly` 컬럼에 있다.

가장 심한 구간은 **2025-10-09 ~ 10-14** 로, 6일간 정상의 0.5% 수준(하루 1만 8천 건)이었다. 결측 검사에도 월별 집계에도 걸리지 않는 형태였다.

---

## 2. 발견: 2025-10 payload 축소

2025-10 부터 payload 평균 크기가 3,481바이트에서 927바이트로 줄었다. GH Archive 체인지로그에 기록된 필드 제거와 일치하며, BigQuery 사본만의 문제가 아니다.

| 타입 | 변화 |
|---|---|
| PushEvent | `commits` 배열, `size`, `distinct_size` 삭제. 758B → 179B |
| PullRequestEvent | `pull_request` 48개 필드 중 43개 삭제. 19,353B → 989B |
| PullRequestReviewEvent | 51개 키 → 19개. 22,358B → 2,919B |
| PullRequestReviewCommentEvent | 66개 키 → 28개. 23,849B → 5,974B |
| 그 외 11개 타입 | 변화 없음 |

**이동한 필드가 있다.** PR 라벨과 담당자는 `pull_request` 안에서 최상위로 올라왔다.

| 이전 (~2025-09) | 이후 (2025-10~) |
|---|---|
| `pull_request.labels` | `labels` |
| `pull_request.assignee` | `assignee` |
| `pull_request.assignees` | `assignees` |

커버리지가 100% 에서 39% / 5% 로 떨어졌지만 손실이 아니다. 이전에는 값이 없어도 빈 배열이 붙어 100% 였고, 지금은 실제로 있을 때만 키가 생긴다.

**실버 테이블로 정규화할 때 두 경로를 모두 읽어야 한다.** 한쪽만 읽으면 해당 시기가 통째로 빈다.

## 3. 발견: 이벤트 건수 감소

payload 축소와는 별개의 현상이 둘 더 있다.

**2025-05 중순, 전체 40% 균일 감소.** 하루 571만 건에서 342만 건으로 떨어졌고, 15개 타입 전부가 0.49~0.65 사이의 같은 비율로 줄었다. 비율이 보존되므로 저장소별 급증 판정(spike ratio)은 유효하다. 다만 절대 건수가 줄어 노이즈가 커진다.

**2024-11 부터 WatchEvent 붕괴.** 이쪽은 균일하지 않다.

| 시점 | WatchEvent | PushEvent |
|---|---|---|
| 2024-11-13 | 271,792 | 정상 |
| 2025-05-14 | 215,319 | 3,542,557 |
| 2025-08-13 | 124,928 | 2,301,746 |
| 2026-08-12 | **2,555** | **3,609,057** |

PushEvent 는 오히려 늘었는데 WatchEvent 는 99% 사라졌다. ForkEvent, PullRequestEvent 도 같은 곡선을 그린다. 현실에서 나올 수 없는 조합이므로 수집 문제로 본다.

WatchEvent 는 GH Archive 에서 스타를 셀 수 있는 유일한 수단이다. **2026년 데이터로는 급증 탐지가 불가능하다.**

## 4. 결정: 분석 창

| 목표 | 창 | 이유 |
|---|---|---|
| 목표 1 (관례 실태) | ~2025-09 | payload 축소 이전 |
| 목표 2 (급증 생존율) | 2022-01 ~ 2025-05 | 결측이 몰린 2021년 회피, WatchEvent 건강 구간 |

목표 2 의 생존 판정은 창 밖으로 나가도 된다. PushEvent 로 T+N개월 활동을 보고, 현재 존재 여부는 GitHub API 로 조회한다. 둘 다 손상 구간에서도 동작한다.

**두 목표 모두 달성 가능하다.** 목표 1은 분석 창을 2025-09 로 끊으면 7개 항목 전부, 목표 2는 payload 를 아예 쓰지 않아 축소의 영향이 없다.

보고서에는 "2025년 9월 기준" 을 명시해야 한다.

## 5. 남은 것

**원본 파일 용량 측정.** 저장 용량 목표가 100GB, 상한 200GB 인데 `.json.gz` 하루치 크기를 몰라 분석 창 폭을 계산할 수 없다. BigQuery 의 하루 14.65GB 는 압축 해제된 컬럼형 크기라 비교 대상이 아니다.

2020 / 2022 / 2024 / 2025 각 하루씩 받아 압축·해제 용량과 시간대별 편차를 잰다. 후보 창 2022-01 ~ 2025-05 는 1,217일이므로, 하루 80MB 면 97GB, 150MB 면 183GB, 300MB 면 상한 초과다.

**미확정 값**

1. 목표 1에서 7개 항목 중 무엇을 실제로 다룰지
2. 목표 2의 최소 절대 증가량 하한
3. 목표 2의 생존 판정 T+N 값
4. baseline 창에서 이상일을 제외하는 규칙
5. 브랜치 수명 계산 시 Create/Delete 매칭 규칙
6. 실버 테이블을 목표별로 분리할지 여부
